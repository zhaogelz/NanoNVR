# NanoNVR：把闲置 Windows 电脑变成单路 RTSP 循环录像机

> 粘贴摄像头的 RTSP 地址即可在本地持续录像。NanoNVR 会自动回收旧片段、预留磁盘安全空间，不需要部署服务器，也不依赖云订阅。

[下载最新 Windows x64 单文件版](https://github.com/zhaogelz/NanoNVR/releases/latest) · [查看 MIT 许可证](LICENSE)

https://github.com/user-attachments/assets/7b1013ee-f84c-44c4-ac6e-81868fe16fb0

当前功能说明以 `v1.2.2` 为基线。

## 为什么做这个项目

很多摄像头可以把录像保存在机身存储卡里，但摄像头损坏或被移走时，录像也可能一起丢失。专用 NVR 更完整，却可能超出单摄像头用户的预算和复杂度需求。

NanoNVR 提供一个更小的选择：复用已有 Windows 电脑，把摄像头码流持续保存到室内硬盘。它不上传录像，也不要求账号或订阅。需要注意的是，单块本地硬盘仍然不是备份；真正重要的录像应及时导出并另存。

## 核心能力

- **单路本地录像**：持续保存一个 RTSP 码流，H.264 和 H.265 均可录制；
- **低额外开销**：直接复制摄像头已经编码好的码流，不重新编码画面；
- **自动循环回收**：按录像配额删除最老片段，并为整块磁盘保留安全空间；
- **运行守护**：发现录像长时间不再增长时自动重连，退出程序时回收 FFmpeg 子进程；
- **回看与导出**：原始 TS 可直接播放，也可按片段合并导出为 MP4。

## 适用场景与边界

适合以下场景：

- 有一台能提供 RTSP 码流的网络摄像头；
- 有一台可以长时间开机的 Windows 电脑或笔记本；
- 希望录像保存在自己控制的硬盘中，不依赖厂商云服务；
- 需要最基本的持续录像、循环回收、状态查看和片段导出；
- 不想为单路录像部署 Docker、数据库或完整监控平台。

以下场景不适合：

- 同时管理多台摄像头；
- 需要浏览器或手机远程查看、时间轴检索、移动侦测、AI 识别或告警通知；
- 需要 Windows 服务、无人值守开机自启、断电重启后自动恢复录像；
- 需要冗余存储、证据级完整性或专业安防系统的高可用能力。

NanoNVR 当前一次只录制一个 RTSP 码流。程序必须保持运行，Windows 也不能进入睡眠；重新开机后需要再次启动程序并点击“启动录制”。

## 快速开始

1. 确认摄像头已经启用 RTSP，并能通过 TCP 访问。H.264 和 H.265 均可录制。
2. 从 [Releases 页面](https://github.com/zhaogelz/NanoNVR/releases/latest)下载最新 `NanoNVR.exe`，放入普通的可写文件夹，不建议放在 `Program Files` 等受保护目录。
3. 双击运行，在“RTSP 流地址”中填写摄像头地址，例如 `rtsp://camera-user:password@192.168.1.100/stream1`。
4. 设置录像配额，单位为 GiB。配额表示自动循环录像允许达到的高水位，不包含用户主动导出的 MP4。
5. 选择保存目录。建议使用容量充足的独立硬盘；留空时默认使用 `NanoNVR.exe` 所在目录。
6. 点击“▶ 启动录制”。程序会保存参数并开始录像。

RTSP 地址可能包含用户名和密码，程序会将它明文保存在 EXE 旁边的 `config.json` 中。不要上传、分享或同步该文件，详见[安全与运行边界](#安全与运行边界)。

## 录像如何工作

NanoNVR 调用 FFmpeg，通过 TCP 接收 RTSP 码流，并使用 `-c copy` 把摄像头已经编码好的视频和音频直接写入 MPEG-TS 文件。程序不重新编码画面，因此 CPU 占用和额外画质损失通常较低；最终写入量仍由摄像头实际码率决定。

正常运行时，录像按日期归档，并约每 15 分钟开始一个新片段。网络中断、摄像头重启或录像停滞时可能产生更短的片段和录像空档。

程序每 10 秒检查最新片段是否继续增长。连续 180 秒没有进展时，它会结束当前 FFmpeg 进程并重新连接。关闭界面或停止录制时，程序会主动回收录像与导出进程；Windows 下还通过 Job Object 降低子进程遗留写盘的风险。

## 文件保存位置

程序目录保存 EXE 和配置：

```text
【程序目录】
├── NanoNVR.exe
└── config.json          # 首次保存参数后生成，可能含明文 RTSP 凭据
```

单文件发布版已经包含 FFmpeg。运行时，FFmpeg 会被解包到 PyInstaller 的临时目录，不会始终作为独立文件出现在 EXE 旁边。

录像和导出文件保存在界面指定的保存目录；留空时才使用程序目录：

```text
【保存目录】
├── 2026-03-01/
│   ├── 08_00_00.ts      # 文件名是片段实际开始时间
│   ├── 08_15_00.ts
│   └── ...
└── exports/
    └── 2026-03-01_08-00-00_12-00-00.mp4
```

显式填写的保存目录不可用时，程序会阻止启动，不会静默回退到系统盘。

## “对硬盘更友好”具体指什么

“对硬盘更友好”不是减少同码率录像的总写入量，也不是延长硬盘寿命的承诺。NanoNVR 能控制的是文件组织、清理节奏和剩余空间。

### 约 15 分钟切片

在码率相同的情况下，1 分钟切片和 15 分钟切片写入的视频数据量基本相同。较长切片的实际作用是：

- 稳定录像时每小时通常只产生约 4 个文件，而不是大量短文件；
- 减少文件创建、关闭、目录项更新和循环删除次数；
- 让机械硬盘的主要负载更接近持续追加，而不是频繁处理零散小文件；
- 将未正常关闭的风险主要限制在当前正在写入的片段，已经关闭的旧片段不需要整体重写。

代价是回看和导出的最小选择单位较粗。由于 `-c copy` 需要在摄像头提供的关键帧附近切换文件，`900` 秒是目标时长，实际片段并不保证严格等于 15 分钟。详见 [FFmpeg segment muxer 文档](https://ffmpeg.org/ffmpeg-formats.html#segment_002c-stream_005fsegment_002c-ssegment)。突然断电时，当前片段仍可能不完整或无法播放，因此切片不能替代不间断电源和备份。

### 配额高低水位

录像占用达到用户设置的 100% 配额后，程序会从最老片段开始回收，直到约 90% 的健康水位。例如配额为 150 GiB 时，一次清理的目标约为 135 GiB。

这样做主要是减少刚越过配额后反复触发小批量删除。程序仍会每 5 分钟统计录像占用并检查磁盘空间，所以它不会消除周期性的容量统计和目录遍历。

### 整块磁盘安全余量

除了录像配额，程序还检查保存目录所在磁盘的真实可用空间，并预留以下两者中较大的值：

- 20 GiB；
- 整块磁盘容量的 5%。

即使其他程序占用了磁盘，NanoNVR 也会提前回收最老录像。清理时会保护最新两个片段和正在导出的片段，并在删除后重新测量空间。如果可回收录像不足以恢复安全余量，程序会停止录制并提示用户处理，而不是继续把磁盘写满。

### 能保护什么、不能保护什么

| NanoNVR 能做的事 | NanoNVR 不能做的事 |
| --- | --- |
| 限制循环录像占用 | 减少相同码率下的视频数据量 |
| 避免磁盘逼近满盘 | 承诺延长机械硬盘或 SSD 的具体寿命 |
| 减少阈值附近反复删除 | 取消每 5 分钟一次的容量检查 |
| 发现录像不再增长并重连 | 修复坏道、过热、供电或震动问题 |
| 退出时回收子进程 | 代替 SMART 监控、不间断电源或异地备份 |

`-buffer_size 10M` 只是 RTSP 网络接收缓冲，用于应对网络抖动，不会减少落盘数据。RAMDisk 也不能减少最终写入量，反而会扩大断电时的数据损失范围，因此本项目不使用 RAMDisk。

## 能保留多少天

可以用摄像头所有码流的总码率做粗略估算：

```text
每天占用（GiB）≈ 总码率（Mbps）× 10.06
达到配额前的天数 ≈ 录像配额（GiB）÷ 每天占用（GiB）
批量清理后的天数 ≈ 录像配额 × 90% ÷ 每天占用（GiB）
```

以 150 GiB 配额为例：

| 摄像头总码率 | 每天约占用 | 达到配额前约保留 | 清理到 90% 后约保留 |
| ---: | ---: | ---: | ---: |
| 1 Mbps | 10.1 GiB | 14.9 天 | 13.4 天 |
| 2 Mbps | 20.1 GiB | 7.5 天 | 6.7 天 |
| 4 Mbps | 40.2 GiB | 3.7 天 | 3.4 天 |
| 8 Mbps | 80.5 GiB | 1.9 天 | 1.7 天 |

这是按持续录像计算的近似值，音频、封装开销、码率波动和断线重连都会影响结果。H.265 通常能在相近画质下降低码率，但节省多少取决于摄像头设置；NanoNVR 不会自动改变摄像头码率或编码格式。

## 回看和导出

### 直接回看 TS

原始录像是未转码的 `.ts` 文件，建议使用 [VLC](https://www.videolan.org/vlc/) 或 PotPlayer。Windows 自带播放器是否能播放，取决于系统是否安装了对应的 H.264/H.265 和音频解码器。

### 导出为 MP4

点击“📤 导出录像”，选择日期、开始片段和结束片段即可生成一个 MP4：

- 视频始终直接复制，不重新编码；
- AAC 音频直接复制，G.711、G.726 等其他音频会转码为 AAC；
- H.265 视频会写入 `hvc1` 标签，以改善 QuickTime 和部分设备的识别兼容性，但播放设备仍需具备 H.265 解码能力；
- 导出速度取决于片段数量、磁盘速度以及音频是否需要转码，不承诺固定耗时；
- 正在增长的最新片段不会参与导出；
- 导出选择以实际片段为单位，因此边界是“约 15 分钟”，不是任意秒级裁剪。

导出的 MP4 位于 `exports/`，不会计入循环录像配额，也不会被自动删除，但仍占用整块磁盘空间。如果导出文件导致磁盘低于安全余量，程序会先回收旧录像；空间仍不足时会停录。使用机械硬盘进行大量导出时，建议把输出路径选到另一块磁盘，减少同盘读写寻道。

## 安全与运行边界

- `config.json` 会明文保存完整 RTSP 地址。不要将它提交到 Git、上传网盘或发送给他人；建议为摄像头创建低权限专用账号，并限制程序目录的文件访问权限。
- 不要把 RTSP 端口直接暴露到公网。需要异地连接时，优先使用受控 VPN，并关闭摄像头默认密码和不必要的公网访问。
- NanoNVR 不会上传录像，但本地录像仍可能包含他人隐私。部署和使用摄像头时应遵守所在地法律并取得必要授权。
- 项目当前没有代码签名，首次运行发布版时 Windows SmartScreen 可能显示风险提示。只运行自己构建或从本项目可信 Releases 页面下载的文件，并核对发布页提供的校验信息。
- 网络中断、摄像头重启、电脑睡眠、程序退出和突然断电都会造成录像空档。当前版本不会在 Windows 启动后自动开始录像。
- 单盘录像不是备份。摄像头、电脑和硬盘同时损坏、遗失或被破坏时，本地录像仍会丢失；重要片段应导出到另一设备或受控备份位置。

## 硬盘维护建议

如果保存目录位于专用的 24 小时录像机械盘，建议避免频繁休眠，并定期查看 SMART 中的温度、通电时间、启停次数、磁头加载/卸载次数、重映射扇区和待定扇区。NanoNVR 不修改 Windows 电源策略，也不替代硬盘健康工具。

使用 SSD 时，应在厂商工具中关注健康度、总写入量和剩余空间。NanoNVR 不修改 TRIM 设置，也不承诺降低 SSD 的 TBW 消耗。

## 从源码运行与构建

仓库代码只依赖 Python 标准库，录像和导出依赖 FFmpeg。

### 运行测试

```powershell
uv run python -m unittest discover -s tests -v
```

### 从源码运行

1. 安装 Python 和 [uv](https://docs.astral.sh/uv/)。
2. 将可信来源的 `ffmpeg.exe` 放在 `recorder.py` 旁边，或确保系统 `PATH` 中存在 FFmpeg。
3. 运行：

```powershell
uv run python recorder.py
```

### 构建 Windows 单文件版

1. 安装 [uv](https://docs.astral.sh/uv/)。
2. 将 `ffmpeg.exe` 放在 `recorder.py` 和 `build_exe.bat` 所在目录。
3. 双击 `build_exe.bat`，或在终端中运行它。
4. 构建产物位于 `dist/NanoNVR.exe`。

构建脚本通过 `uvx pyinstaller` 临时调用 PyInstaller，并把 `ffmpeg.exe` 作为独立二进制资源封入单文件程序。目标电脑不需要安装 Python、FFmpeg 或 uv。

FFmpeg 是独立的第三方项目，不适用 NanoNVR 的 MIT 许可证。自行构建或分发时，请选择可信且许可证适合自身用途的 FFmpeg 构建，并遵守 [FFmpeg Legal](https://ffmpeg.org/legal.html) 与对应构建的许可证、源码提供和署名要求。
